# Incident: Full Network Outage, October 15, 2026

## Summary

The router stopped responding to all wired and wireless clients during an evening of stacked configuration changes. A power cycle restored it. After recovery, the gaming VLAN still could not resolve DNS. The investigation then uncovered several latent problems unrelated to the outage itself.

## Timeline

| Time | Event |
|---|---|
| Evening | Automated quarantine installed: a Pi script used a passwordless root SSH key to edit the router's nftables. |
| Late evening | Packet mirroring attempted with `opkg install iptables-mod-tee`. Install hung at "Configuring kmod-ipt-tee." |
| Shortly after | Router unresponsive; all Wi-Fi and wired access lost. |
| ~23:30 | PC self-assigned 169.254.x.x (no DHCP). With a static address the link was up but the router did not reply. |
| ~23:31 | Router power-cycled and recovered. |
| Oct 16, 00:03 | Log rotation left Suricata unable to write its logs (found later). |
| Oct 16, 06:03 | Pi rebooted; Suricata was not restarted with the other containers. |
| After recovery | Gaming PC could reach IPs but not names: DHCP was handing out the Pi as DNS. |

## Root cause analysis

**Primary (likely, not proven):** the hung kernel module install. After reboot the package was absent and no module was loaded. Proof was impossible because router logs were held in RAM only.

**Secondary (confirmed):** `dhcp_option '6,<pi address>'` on the gaming VLAN. The firewall blocks that VLAN from the Pi's DNS port, so name resolution failed while raw IP traffic worked.

**Troubleshooting errors:**

- A port was referred to by internal switch number instead of its case label, which sent the PC cable to the wrong network.
- A static-address test left a persistent setting behind on the PC.

## Latent issues discovered

1. The quarantine was never persistent. The same nftables block had been appended to `/etc/firewall.user` four times, and fw4 ignores that file.
2. The Pi held an unrestricted root key to the router.
3. The quarantine whitelist omitted the PC and phone, so a noisy alert could isolate them.
4. dnsmasq had been changed to answer DNS from any source.
5. The alert topic name was exposed in screenshots.
6. The main Docker Compose file was missing, leaving 14 containers undefined.
7. Suricata ran without logging after rotation (UID mismatch: container user 998, files owned by 1000), then stayed down after a reboot.

## Remediation

| Issue | Fix |
|---|---|
| Non-persistent quarantine | Moved to `/usr/share/nftables.d/table-post/`, which fw4 includes on every load |
| Root key on the Pi | Replaced with a forced-command key limited to add, del, and list |
| Wrong DNS on the gaming VLAN | DHCP option removed; every VLAN uses its own gateway for DNS |
| Open DNS resolver | `localservice` restored |
| Suricata logging | Ownership fixed; rotation switched to `copytruncate` running as root |
| Missing Compose file | Regenerated from running containers and stored privately |
| No crash evidence | Router syslog now shipped to the Pi |

## Process failures and rules adopted

| Failure | Rule adopted |
|---|---|
| No backup before live changes | Back up and copy off-box before any router change |
| Many changes stacked untested | One change, verify, record |
| AI output applied without review | Review every command; verify persistence, not just success |
| DNS dependent on the Pi | Router is the DNS server for every segment |
| No persistent logs | Logs shipped off the router |
| Kernel module from the generic feed | No `kmod-*` installs on vendor firmware |
| Unchecked firewall restarts | `fw4 check` before every restart |
